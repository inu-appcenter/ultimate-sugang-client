# 02 — API 계약 명세 (API Spec)

> **출처**: `intake/INU-수강신청-모의사이트-명세.md` 원§0·§4·§9·§10·§12·부록. 원본 명세의 §는 `원§n` 으로 표기.
> **성격**: **사용자 명세의 사실 재구성만.** 하네스 창작 없음.
> **⚠️ 계약 상태: 엔드포인트 미제공.** 명세는 "서버·API 는 별도 존재"(원§0)라고만 하며 엔드포인트·메서드·URL·응답 envelope·상태코드를 정의하지 않는다(부록: "서버 엔드포인트·파라미터 — 모의 사이트에 불필요"로 미조사). 따라서 이 문서는 **(a) 데이터 모델 (b) 화면이 필요로 하는 오퍼레이션 목록(계약 아님) (c) 서버 검증 규칙 (d) 메시지·에러 종별 (e) enum/코드 (f) 서버 시뮬레이션 요건** 만 수록한다. HTTP 계약은 🙋🏻 **Q-1**. 하네스는 `03 §3` 의 어댑터 인터페이스(mock 기본, D1)로 이 gap 을 우회하되, **엔드포인트를 창작하지 않는다.**
> **관할**: API 계약·필드·enum·토큰 정책. 동작 = `01`, 프론트 계획 = `03`.
> **개정 2026-09-06**: D25(계약 도출 순서)·D26(시드·모델 정정)·D27(`isEnglish`)·D28(이수구분 8종)·D23/D24(O-12~14 처리). 시드 = `intake/INU-시드데이터.md`.

## §2. 데이터 모델 (원§12 "데이터 모델 최소 스키마")

### §2-1. `Course`
| 필드 | 타입(추정 표기) | 의미 / 관측값 | 화면 |
|---|---|---|---|
| `id` | string | 식별자 | 신청 요청 키 |
| `code` | string | 학수번호. 예 `0006154050`, `IAA6066001`, `0012410001` | 학수번호 |
| `name` | string | 한글 교과목명. 예 `현장교육.실습(Ⅴ-1)`, `대학수학(2)` | 교과목명(굵게) |
| `nameEn` | string | 영문명 **원문(괄호 없음)**. 예 `INTERNSHIP(Ⅴ-1)`, `C language programing (2) `(끝공백 원문). 표시 시 `( )` 로 감쌈(D26) | 교과목명 2행 |
| `professor` | string | 교강사. 예 `최승식` | 교강사 |
| `credits` | number | 학점. 예 `12` | 학점 |
| `capacity` | number | 정원 — **화면 비노출** | — |
| `enrolled` | number | 신청인원 — **화면 비노출** | — |
| `courseType` | enum(§5-6 8종) | 이수구분(**개설학과 기준**). 관측 `전공심화` 등(D28) | 이수구분(조회) |
| `courseArea` | string | 이수영역(교양). §5-1 코드/명 | 이수영역(교양) |
| `department` | string | 개설학과. 예 `컴퓨터공학부` | 개설학과 |
| `grade` | string | 학년. 관측 `전학년` | 학년 |
| `schedule` | string | 시간표 **원문 문자열**(`01 §3-4` 문법, D26). 예 `월 1 2 3 … (ZZ-102)`. 온라인 = 빈 문자열 | 요일 및 교시(강의실) |
| `tags[]` | enum[](§5-5 5종) | 값은 이름(`75분수업` …), 표시 `[이름]`(D26) | 교과목명 태그 |
| `isEnglish` | boolean | 원어 강좌 → 원어여부 셀 `EN(원어)`(시드 §5 관측, **D27**). 전체 5% 내외 | 원어여부 |
| `isNight` | boolean | 야간학과 → 행 `brown` | 행 색 |
| `isClosed` | boolean | 마감 → 행 `grey` + 액션 `마감` | 액션 |

> 2026-09-06 개정: 원어여부 → `isEnglish`(D27), `schedule` 은 문자열(D26)로 확정. 시드 문서 필드명 대응 `nameKo`→`name`, `credit`→`credits`. mock 은 `id` = 학수번호.

### §2-2. `Enrollment`
| 필드 | 타입 | 의미 |
|---|---|---|
| `studentId` | string | 학생 |
| `courseId` | string | `Course.id` |
| `resolvedType` | string | **학생 기준 재계산된 이수구분**(`01 §3-2`). 관측: 조회 `전공심화` → 신청내역 `일반선택` |
| `reAttendance` | string | 재수강 구분. 신규 신청 시 빈 값 |
| `createdAt` | datetime | 생성 시각(형식 미기재) |

> 신청내역 표시에는 `Course` 의 학수번호·교과목명·학점·원어여부·시간표·개설학과·교강사가 함께 필요하다(`01 §5` 신청내역 11컬럼). 최소 스키마에는 `courseId` 만 있으므로 **조인 형태(내장 vs 별도 조회)는 계약 gap** → Q-1. mock 어댑터는 `Course` 를 내장해 반환한다(`03 §3`).

## §4. 서버 검증 규칙 · 에러 종별 · 메시지

### §4-1. 검증 우선순위 (원§10.1 — 백엔드 검증, 프론트는 UI 차단 + 메시지 표시)
```
1. CAPTCHA 통과          실패 시 요청 보류, 재시도     (모의: VITE_CAPTCHA=on 시 D34 게이트, 기본 off)
2. 시간표 중복 검사       → DUP_TIME
3. 동일 과목명 검사       → DUP_SUBJECT      (2 와 독립 — 시간 미겹침에도 차단)
4. 학점 상한 검사         → CREDIT_EXCEEDED  (미관측, 메시지는 명세 제안)
5. 정원 검사             → CLASS_FULL       (마감 버튼으로 사전 차단)
```
프론트 UI 차단: `isClosed` 행은 `마감` 버튼(클릭 불가). 나머지는 서버 응답에 따름.

### §4-2. 이수구분 파생 (원§10.2)
`Enrollment.resolvedType` 은 서버가 `(학생 소속 × 강좌 개설학과)` 로 산출. 프론트는 재계산하지 않고 값을 표시한다.

### §4-3. 에러 종별 ↔ 메시지 카탈로그 (프론트 내부 코드 — HTTP 표현은 Q-1)
| 코드 | 채널 | 메시지(원문 그대로, `\n` + 공백 1칸 + 영문) | 출처 |
|---|---|---|---|
| (성공) `ENROLL_OK` | alert | `{교과목명} 교과목 신청이 완료되었습니다.\n Application completed.` | 원§9.2 |
| (확인) `CANCEL_CONFIRM` | confirm | `신청하신 과목을 취소하시겠습니까?` | 원§9.2 |
| (성공) `CANCEL_OK` | alert | `수강취소가 완료되었습니다.\n Application canceled.` | 원§9.2 |
| `DUP_TIME` | alert | `신청된 교과목과 시간이 중복되어 신청할 수 없습니다.\n Duplicated time table.` | 원§9.2 |
| `DUP_SUBJECT` | alert | `동일한 과목명을 이미 신청 하였습니다.\n Duplicated Subject.` | 원§9.2 |
| `CREDIT_EXCEEDED` | alert | `신청 가능 학점을 초과하여 신청할 수 없습니다.\n Credit limit exceeded.` | 원§9.3 제안 → D6 |
| `CLASS_FULL` | alert | `해당 강좌는 마감되었습니다.\n Class is full.` | 원§9.3 제안 → D6 |
| `SESSION_EXPIRED` | alert | `세션이 만료되었습니다. 다시 로그인하세요.\n Session expired.` | 원§9.3 제안 → D6 |
| `NOT_IN_PERIOD` | alert | `수강신청 기간이 아닙니다.\n Not in registration period.` | 원§9.3 제안 → D6 |
| `TIMEOUT` | alert | 명세 없음 → `03 §5-3` 하네스 기본 문구(Q-13) | 원§12 "타임아웃" 언급만 |

## §6. 서버 시뮬레이션 요건 (원§12 — **백엔드 범위**, 프론트 대응은 `01 §8`)
| 요소 | 요건 |
|---|---|

mock 어댑터(D1)는 이 중 **지연·검증(§4-1 2~5)·파생 이수구분(§4-2)** 만 시뮬레이션한다. 동시 경쟁·대기열·서버 시계는 실 백엔드 몫(`03 §3-4`).

## §8. 계약 도출 방향 (D25, 2026-09-06)
- 계약(엔드포인트·envelope)은 **먼저 주어지지 않는다**. 순서: 프론트 mock 완성 → 완성도 비교 → **프론트가 예측하는 API Spec 도출**(`03 §3-2` `SukangApi` 인터페이스 + 본 문서 §2 모델이 기준) → 서버 API 를 그 Spec 에 맞춰 수정.
- 따라서 `http` 어댑터는 착수하지 않는다(스텁 유지). mock 어댑터 인터페이스를 깔끔히 유지하는 것이 Spec 도출의 전제.
